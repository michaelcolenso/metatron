### Blocker: `.github/workflows/deploy.yml` change could not be pushed
Both write paths available in this session — `git push` and the GitHub API (via the GitHub App/MCP integration) — were rejected with the same error: `Insufficient scope: required "repo workflow"`. GitHub requires the OAuth `workflow` scope specifically to touch any file under `.github/workflows/`, separate from general repo write access, and neither credential configured for this session has it. This isn't something retrying or switching tools works around — both paths hit the identical platform-level restriction, confirming it's a credential-scope gap, not a bug.

### Review round: three more verified and fixed
A Codex review on this PR caught three real issues, each verified against the actual code/lockfile before fixing:
- **P1 — schema crash risk**: because of the Blocker above, the old workflow could still overwrite `docs/images.js` with the legacy `sizes`/`hasWebP` schema before the pending fix lands, and the new `docs/script.js` would throw on `undefined` `sizeInfo.webp` — an empty, broken gallery, not just a missed optimization. Fixed with a `getSizeInfo()` normalizer in `docs/script.js` that handles either schema; verified by serving a fixture built from the actual old catalogue format and confirming it renders with zero errors instead of crashing. This doesn't remove the need to apply the pending workflow fix — it just means the site degrades to "old-style full-res images" instead of breaking outright if the old workflow fires first.
- **HEIC opt-in didn't persist**: a HEIC photo published via `INCLUDE_HEIC=1` was silently un-published (catalogue entry and all 5 derivative files removed) on the very next ordinary `npm run update-images` run, contradicting the "one-time opt-in" framing above. Fixed in `scripts/update-images.js` so a photo already published this way stays published without needing the env var again — verified end-to-end (published all 8, ran again without the flag, confirmed all 8 survived; then manually restored the pre-test state so this PR's actual default — all 8 unpublished — is unchanged).
- While verifying that fix, found that **6 of the 8 ".HEIC"-named source files are actually already JPEG** (confirmed via magic bytes, not just a failed decode) — a common export/transfer mislabeling. `heic-convert` correctly failed on them and the existing per-file error isolation correctly skipped them without crashing the run, but they were being treated as unsupported when they're already web-ready. Fixed to detect and pass them through as-is (no unnecessary lossy re-encode); only the genuine 2 HEIC files go through `heic-convert`. Still gated behind the same `INCLUDE_HEIC` opt-in either way — this changes what happens *if* you opt in, not whether you're opted in by default.
- Also caught and fixed: `sharp@0.35.4` requires Node ≥20.9.0 per its own lockfile, contradicting this README's "Node 18 or newer." Raised the documented minimum to match (the CI workflow already used Node 20).

## Findings that need your call (not changed here)

### 1. Every "thumbnail" is the full-resolution original — real page-weight problem
`docs/script.js` sets `img.src = images/${photo.name}` for every grid card and the lightbox alike. There is no `srcset`, no `<picture>`, no actual resized asset. `docs/images.js` *does* carry a `sizes: { thumb, medium, full }` field per photo, but those `thumb_*`/`medium_*` files don't exist anywhere in the repo (confirmed: zero files match `thumb_*`, `medium_*`, or `*.webp` in the whole tree) — the field is aspirational and currently dead. The largest source photo is 8.6MB; loading a 31-photo masonry grid currently means downloading the full 40MB of `docs/images/` on first paint for every mobile visitor.
**Recommendation:** either (a) generate real thumb/medium variants at build time and wire up `srcset`/`sizes`, or (b) if that's more than this project needs, drop the unused `sizes`/`hasWebP` fields from the data model so the schema stops implying a capability that doesn't exist. I'd lead with (a) — it's the single highest-impact change for an image-heavy site — but it's a scoped follow-up, not a drive-by fix.
**Resolution:** implemented (a). `scripts/update-images.js` now generates real `thumb` (480px) and `medium` (1400px) derivatives in JPEG + WebP per photo via `sharp`, with real recorded width/height; `full` stays a byte-identical copy of the source (never re-encoded, so showcase fidelity is untouched). `docs/script.js` renders the grid with `<picture>` (WebP + JPEG fallback) at the `thumb` tier, and the lightbox with a `srcset` across `medium`/`full` so the browser only pulls full-resolution when the viewport/DPR actually calls for it. Measured in headless Chromium: the 31-card grid now downloads **~0.3MB total** (was ~40MB worst case), all as WebP; opening a photo typically loads ~150–250KB (the `medium` tier), occasionally the full original on a large/high-DPI viewport where the responsive algorithm correctly picks it. Old `sizes`/`hasWebP` fields are gone from the schema, replaced by `full`/`thumb`/`medium` objects with real files and dimensions.

### 2. Two independent, conflicting image-pipeline implementations
- `scripts/update-images.js` (committed, uses `exifreader`, run manually via `npm run update-images`) — writes `hasWebP: false`, never resizes, just copies originals.
- `.github/workflows/deploy.yml` (inline heredoc, uses `exiftool-vendored` + ImageMagick, installs its own throwaway `package.json` at runtime) — writes `hasWebP: true`, actually resizes and creates WebP variants.

They produce different `docs/images.js` schemas from the same source photos. Evidence the two have already diverged in practice: **every entry in the current `docs/images.js` says `"hasWebP": false`**, and the last catalogue regeneration (commit `08019b6`, "Regenerate image catalogue with EXIF metadata") was done by running the local Node script, not by the workflow — meaning the CI pipeline's ImageMagick/WebP step hasn't actually been the one in effect for a while, despite still being wired up to run on every push to `images/**` and every Sunday via cron.
**Recommendation:** pick one canonical pipeline and delete the other. If you want the resized/WebP variants from finding #1, that argues for keeping and fixing the CI version (and pointing `script.js` at the generated sizes); if you want a single, simple, locally-run script, retire the CI image-processing steps and keep `scripts/update-images.js` as the only path.
**Resolution (⚠️ written, not yet live — see the blocker note at the top of this doc):** kept `scripts/update-images.js` as the single canonical pipeline (it was already the one actually in effect, is reviewable committed code rather than a YAML heredoc, and needed no system packages). It now does everything the CI version did — resize, WebP, EXIF — properly. `.github/workflows/deploy.yml` no longer has its own separate image-processing logic; it now just runs `npm ci && npm run update-images` (the exact same script a contributor runs locally) and commits the result. One pipeline, used everywhere.

### 3. GitHub Pages deployment path is ambiguous from the repo alone
`README.md` tells contributors to configure Pages as "Deploy from a branch → `/docs`". `.github/workflows/deploy.yml` instead deploys via `actions/deploy-pages` (the "GitHub Actions" Pages source) — and only runs automatically on pushes that touch `images/**`, plus the weekly cron. GitHub Pages can only have one active source at a time, so one of these two mechanisms is currently not the one actually serving the site. This matters concretely: if Pages is set to the Actions source, then a commit that only touches `docs/styles.css` or `docs/script.js` (like the recent masonry-layout change) would **not** auto-deploy — no path in the workflow trigger covers non-image `docs/` edits, so it would sit unpublished until the Sunday cron or a manual `workflow_dispatch`.
**Recommendation:** check Settings → Pages on the actual repo, confirm which source is live, and delete the unused mechanism. If Pages is Actions-sourced and you want hand-edited `docs/` changes to auto-deploy, don't just widen the trigger to `docs/**` — the workflow's own "Commit changes" step pushes into `docs/images/**` and `docs/images.js`, both under `docs/`, so a bare `docs/**` filter would make the workflow retrigger itself on its own generated commit. List the hand-edited files explicitly instead (`docs/index.html`, `docs/styles.css`, `docs/script.js`) or exclude the generated image paths.
**Resolution (⚠️ written, not yet live — see the blocker note at the top of this doc):** made the repo internally consistent with the branch-deploy option README already documented, since it needs zero workflow involvement (any push to `main` auto-publishes `docs/` once Pages is set to "Deploy from a branch"). Removed `actions/configure-pages`, `actions/upload-pages-artifact`, `actions/deploy-pages`, the `github-pages` environment, and the `pages`/`id-token` permissions from the workflow — its only remaining job is regenerating the catalogue (see #2). This also fully closes the self-triggering-loop risk: there's no separate Pages-deploy trigger to widen. **One thing I can't verify or change from a checkout: confirm Settings → Pages on the actual repo is set to "Deploy from a branch: `main` / `/docs`."** If it's currently set to "GitHub Actions" instead, flip it — that's a one-time dropdown change, not a code change.

### 4. Eight source photos are dead weight — and the CI pipeline isn't even safe around them
`images/*.HEIC` (`IMG_4952`, `IMG_5189`, `IMG_6001`, `IMG_6652`, `IMG_6897`, `IMG_7578`, `IMG_7621`, `IMG_7621(1)` — 8.9MB total) never reach the published gallery today, but the two pipelines don't agree on why. `scripts/update-images.js` (the one actually in effect — see #2) filters to `.jpg/.jpeg/.png` and skips them cleanly. `.github/workflows/deploy.yml`'s "Process images" step does **not** filter by extension — its `for img in images/*` loop runs `exiftool`/`convert` on every file, HEIC included — so if that pipeline is ever relied on again, it will attempt to convert these too, and either produce unlisted derivatives or hard-fail the step (stock Ubuntu ImageMagick often lacks HEIC/libheif support), depending on the runner's codec support. HEIC also doesn't render in Chrome/Firefox/Edge regardless of pipeline.
**Recommendation:** either convert them to JPEG and let them into the catalogue (if you want those photos published) or delete them (if they were already superseded/rejects). If you keep the CI pipeline at all (see #2), give its shell loop the same extension filter either way — right now it's one HEIC upload away from breaking the whole job.
**Resolution:** the unsafe unfiltered CI loop is gone entirely (see #2). `scripts/update-images.js` now has real HEIC/HEIF decode support (via `heic-convert`, converting to a high-quality JPEG since browsers can't render HEIC directly) with per-file error isolation — a bad or unconvertible file is skipped with a warning, never crashes the run. It's **off by default**: these 8 files are still excluded from the published gallery today, exactly as before. Publishing them is a one-line opt-in (`INCLUDE_HEIC=1 npm run update-images`) left for you to trigger — deciding which personal photos go on a public portfolio isn't something to default into as a side effect of a pipeline fix.

### 5. Repo/`.git` size is large for the content (134MB `.git`, 89MB of tracked image bytes across `images/` + `docs/images/`)
Git history shows several full add/delete/re-add cycles for the images directory ("image reset", "Delete images directory", "Add files via upload" ×2+), so old full-resolution blobs are retained in history on top of the current 89MB working tree. Not urgent, but it'll keep growing every time photos churn.
**Recommendation:** no action needed now. If it becomes a real problem later, `git filter-repo` can reclaim the history bloat, but that rewrites history and force-pushes — flagging it here rather than doing it, since it's destructive and affects anyone else with a clone.
**Resolution:** unchanged, per the recommendation above — this was never a "fix later" item, it was "don't do this without a specific reason and explicit sign-off." Note `docs/images/` itself is now ~50MB rather than ~40MB, since the new `thumb`/`medium` derivatives are *added* alongside the untouched full originals (nothing was removed) — that's expected and is unrelated to the `.git` history-bloat issue described here. The new pipeline does prevent *future* growth of this kind: it deletes derivative files that no longer correspond to a current source photo, so renamed/removed photos don't leave orphans behind (verified: removing a source photo and re-running the script cleaned up all 5 of its derivative files; restoring it and re-running brought them back).

### 6. Minor/cosmetic
- No favicon (`docs/index.html` has no `<link rel="icon">`) — every browser silently 404s on `/favicon.ico`. Harmless but easy to fix.
  **Resolution:** added a small inline SVG data-URI favicon (simple lens/aperture glyph, no extra asset file needed).
- Several source filenames contain spaces and repeated `Copy`/`Copy Copy Copy` suffixes (e.g. `IMG_2201 Copy Copy Copy.JPG`, `IMG_1006 Copy.JPG`) — browsers handle the spaces fine via URL auto-encoding, so nothing is broken, but it suggests these are unreviewed export duplicates worth a pass.
  **Resolution:** left the filenames alone (this was explicitly "nothing is broken," not a bug) — but the new `srcset`-based responsive images in #1 exposed a *real* related bug: srcset's micro-syntax uses whitespace as a delimiter, so an unencoded space in a filename silently corrupted that candidate and made the browser drop it, falling back to JPEG for exactly the space-named files. Fixed by URL-encoding every filename used in `src`/`srcset` (`docs/script.js`); verified in Chromium that all 31 photos, including the space-named ones, now correctly load WebP.
- For at least one photo, `title` and the displayed date are identical strings shown twice in the lightbox (title defaults to the formatted date when no better title exists) — cosmetically redundant, not a bug.
  **Resolution:** fixed — both the grid hover overlay and the lightbox caption now skip the title line when it's identical to the formatted date, in `docs/script.js`.
- No automated tests. Reasonable for a site this size, but the one piece of real logic — EXIF/filename date-parsing fallback chains in `scripts/update-images.js` — is exactly the kind of thing that silently regresses without a test, if you ever touch it again.
  **Resolution:** not added (still no test runner in this project; introducing one is a bigger call than this pass warrants). Did fix a real bug this logic had, found while regenerating the catalogue: two photos with neither a filename-date nor EXIF date were falling back to the filesystem `birthtime`, which is meaningless in a git checkout (it showed `1970-01-01` for one prior run, and today's checkout time on this one — both fabricated). Removed that fallback entirely; such a photo is now left undated (sorts to the end, title falls back to a humanized filename) instead of showing a made-up date.
